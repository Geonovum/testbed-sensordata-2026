# Conclusion

Geonovum started this testbed wanting to learn more about what would be needed to make the SensorThings API a broadly adoptable standard for gathering and querying sensor data in the public sector. In particular, Geonovum wanted to learn whether making the SensorThings API a mandatory standard would be beneficial, and what would need to be solved before we could do this. The testbed taught us a number of important lessons and confirmed others.

## What works well

First of all, the SensorThings API model is easy to implement. All participants succeeded in this, even for completely new domains that had never been used in conjunction with the SensorThings API before: [municipal waste containers](#x1-2-how-a-waste-container-becomes-sta-entities) at Clappform, and [climate adaptation monitoring at urban living labs](#what-worked-well) at Geo Insights. Clappform mapped that unfamiliar domain onto the seven core entities [with no extensions and no compromises](#x5-1-the-entity-model-needs-no-extensions), Collaborall confirmed that the v1.1 entity model [maps one-to-one onto OMS concepts](#data-model-oms), and Fraunhofer reports that [setting up a server with the core data model is trivial](#conclusions). This shows the model serves its purpose very well.

The use of the SensorThings API facilitates interoperability. The testbed has shown this with practical, quantifiable results. For instance, Clappform was able to [connect to the Collaborall server in a matter of days](#x7-1-the-evidence-integrating-a-stranger-s-server-took-days) without outside help — no documentation, no schema, no SDK and no contact with the other party's engineers — where a comparable vendor integration usually takes them weeks. TU Delft could [point their client at multiple unrelated servers](#benefits-of-using-sta) without any issue, by changing only the target endpoint.

When using the SensorThings API you put harmonisation right at the edge, when ingesting sensor data. As TU Delft [put it](#recommendations-0), the SensorThings API is the integration contract, not the IoT manager or the decoder. Clappform noted that the effort of conforming to the SensorThings API was [by far the cheapest part of the work](#x3-where-the-effort-went), compared to the other things you have to do regardless of harmonisation when configuring sensors for data ingestion: network access, concurrency, authentication and idempotency. Collaborall reached the same conclusion from the connector side and reads it as [an argument for the standard](#lessons-learned-0): the translation problem is real, but it only has to be solved once, at the edge. These are major arguments for using the standard. It costs little extra effort and provides interoperability at every stage of using sensor data after ingestion.

## What needs attention

When implementing the SensorThings API there are things that need attention. Each participant has mentioned their lessons and recommendations in their own chapters. From the Geonovum perspective the following stood out.

### Conformity does not guarantee interoperability

The SensorThings API standard allows for a lot of freedom in semantics. This is what makes it such a broadly applicable standard, but it comes with the danger of having two conforming implementations in the same domain that do not understand each other. Clappform found [four different definitions of "CO₂ level" on a single, entirely valid server](#x4-8-well-formed-sta-data-can-still-be-hard-to-use), with units written as `"..."`, and concluded that they had achieved interoperability of form but not of meaning. Geo Insights [arrived at the same conclusion independently](#issues-at-the-standard-level), and TU Delft recommends [closing the set of names and definition URIs](#domain-specific-canonical-field-enumerations-and-value-codes) in middleware. When making the SensorThings API a national standard this should be addressed in some way, for instance by letting specific domains make their own semantically interoperable data model extensions. Both Clappform and Geo Insights note that this is the one layer a national profile can pin down [without any change to the specification](#x6-1-bind-the-semantics-a-controlled-vocabulary-for-definitions-ucum-for-units).

### Modelling conventions

Regardless of domain, it would also be beneficial to have modelling conventions: conventions on the granularity of Things, naming conventions, how to deal with sensor arrays, derived time series, and so on. The standard allows a lot of freedom in these. Geo Insights states the problem concretely: should a weather station with five parameters be [one Thing with five Datastreams, or five Things](#issues-at-the-standard-level)? The standard allows both, but only consistent choices enable meaningful queries across datasets. TU Delft worked out preferences for [sensor arrays](#modelling-sensor-arrays), [derived observations](#real-and-derived-observations) and [equivalence and identity](#equivalence-and-identity). A national standard would improve interoperability by making more of these choices on a national level.

### Implementation choices the standard leaves open

Another important lesson is that there are implementation choices that the standard leaves open which can still lead to interoperability problems. Collaborall found a number of these while [implementing their server from the specification](#lessons-learned), and observed that because FROST was the only other server in use, the behaviour of the reference implementation has quietly become part of the standard. Geo Insights met the same class of problem from the client side, including [a server that silently rejected every observation for weeks](#issues-with-server-implementations), and Clappform sets out [how to tell an implementation defect from an ambiguous specification](#x4-10-whose-problem-is-it-the-implementation-the-deployment-or-the-standard), because the two have very different remedies. A centralised interoperability test suite with support for national profiling would be a way to address this, and three participants recommend one independently.

### Which version to mandate

The published version of the standard is 1.1. Version 2.0 had not finished its formal approval process at OGC at the end of the testbed, but Fraunhofer [has already implemented it](#the-sensorthings-api-version-2-data-model) and made a 2.0 server available during the testbed, and it solves a significant number of the issues found here: a `definition` attribute on almost all entities, [direct linking of Features to Datastreams](#features-featuretypes-and-ofinterest), and [explicit typing of observation results](#observation-result-type). Still, at Geonovum we regard 2.0 as the better candidate for a mandatory standard, both for the benefits it has and because the gap between 1.1 and 2.0 is not so large that it would put a major burden on implementers: TU Delft supports 1.1 and 2.0 in [an almost identical codebase](#sensorthings-api-v2) and also recommends 2.0. Geo Insights did find the payload differences [significant enough to require an adaptation layer](#issues-at-the-standard-level). The installed base of sensorthingsAPI is low in the Netherlands at the moment making the overall impact low.

### Best practices for implementation and governance

In addition to a standard, national profiles and interoperability testing, a best practice for implementing the standard would also add value. For instance, the testbed found several error conditions and misconfigurations that the standard and its implementations do not alert you to. Clappform's most serious defect was a poll cursor that [advanced into a forecast horizon and discarded every real measurement](#x4-11-a-vendor-s-forecasts-would-have-truncated-our-history-without-warning) up to that date, without logging an error and while the stream still looked healthy. In the same chapter, a [dead sensor turns out to be invisible rather than stale](#x4-12-a-container-is-only-published-once-it-reports-so-a-dead-sensor-is-invisible-rather-than-stale), and concurrent writes [duplicated shared entities in silence](#x4-4-a-concurrency-race-duplicated-shared-entities-in-silence) because the standard does not require entity names to be unique. Geo Insights adds the operational failures that only appear under sustained load, and concludes that [watchdogs, alerting and an external freshness check belong in the design from day one](#lessons-learned-1). Knowing what these are and how to check for them will save implementers a lot of time.

Governance around sensor networks and uniform policies for onboarding — that is, all the non-technical, contractual and organisational issues that need to be solved for interoperability — would equally benefit from suggested best practices. This was the clearest single finding for Geo Insights, who could not connect [two of their five fieldlabs](#fieldlab-onboarding-experiences) during the testbed period even though the technical side was ready, and for whom governance took more calendar time than writing code. When sensor networks also harmonise at the organisational level, this would help re-use and interoperability a lot.

## Future work

The conclusions already have recommendations in them that can be worked out in more detail. In addition there are important issues that were out of scope for this testbed but need to be addressed before making the SensorThings API a mandatory standard.

First of all, there are competing standards, both internationally and nationally, that partially overlap with the functionality of the SensorThings API. Within OGC there is the Connected Systems API, which was investigated in the 2025 Geonovum testbed on sensor data. On a national level there is the Digitale Delta API standard for observing water levels, and the Key Register of the Subsurface (BRO), which has implemented its own interface for sensor data on groundwater levels. There are also related standards, for instance IM Metingen, a Dutch profile of Observations & Measurements that is currently used in multiple standards that incorporate observations and could also be used in conjunction with the SensorThings API.

STAplus is an extension to the SensorThings API 1.1 that solves some of the issues raised in this testbed but was out of scope. TU Delft notes that it [adds concepts of ownership to the data model](#extensions-and-the-future-of-the-standard), which is precisely the gap Collaborall reports from both [the server side](#lessons-learned) and [the connector side](#lessons-learned-0). We would need to look into whether this could be part of a national profile, and whether it is compatible with the SensorThings API 2.0.
